# Make the budget view v2's primary view, keeping the production view alongside

v1 judged decisions in the production view: the top 8 reranked chunks inside the token budget, as a production system would send them. A fixed cap of 8 handicaps small chunks at large budgets - at 1024 tokens a 128-token chunking could pack about twice as many chunks as the cap allows, while a 512-token chunking never comes near it - so part of a small chunking's gap in v1 came from the cap alone, which v1's fair view was kept to show. v2 adds contenders built on small chunks (late chunking on fixed 128-token windows), so the choice of view now moves the verdict itself, not a side table.

So v2's primary view is the budget view: as many reranked whole chunks as fit the token budget, at most 20 per question. v1's production view (top 8) is reported alongside, so v2's numbers stay comparable with v1's. The alternatives were keeping the production view primary, which would score small chunks under a cap sized for large ones; the fair view with no cap at all, which is not what a reader can be sent; and a higher fixed top-N cap without a budget, which re-creates the top-k unfairness ADR 0001 was written to avoid.
